# 04 How keystone works: findings

Ticket: [04 How keystone works](../decisions/04-how-keystone-works.md). Researched 2026-10-19. Web research only. Nothing was run and no device was touched.

## Short answer

On H713 projectors of this family, keystone is not only a launcher screen. It has three parts, and only one of them is the launcher:

1. **The warp itself** happens in the system's display compositor. On the HY310's stock Android 11, a vendor-modified SurfaceFlinger (Android's screen compositor) calls a vendor library, `libkeystone.so`, and bends the whole picture on the GPU. Apps send it the corner values with a SurfaceFlinger binder call, transaction **1050**. Any app that is allowed to make that call can drive keystone. (High confidence for the HY310, medium for the HY320.)
2. **Automatic keystone** runs in **`com.hysd.vafocus`**, not in the launcher. Its `LocalService` reads the tilt sensor, works out the corners with its native library `libduRYXtp.so`, saves them in `persist.htc.keystone.*` system properties and sends them to SurfaceFlinger. (High confidence for the HY310, medium for the HY320.)
3. **The manual keystone screen and the projection-orientation screen** live in the stock launcher. (High confidence for the screens. How orientation is applied underneath was not found.)

So automatic keystone **probably keeps working without the stock launcher, as long as `com.hysd.vafocus` stays installed and enabled**. Two things are still unknown: whether vafocus starts by itself at boot, and where the auto-keystone on/off switch is stored. Only this unit can answer both.

**This corrects the earlier research.** [02b](02b-planning-facts-data.json) said vafocus "has nothing to drive" on a manual-focus HY320 and "loses nothing if removed". That is wrong. On the HY310, vafocus is the auto-keystone engine. **Keep `com.hysd.vafocus` on the keep-list until the unit proves otherwise.**

Do not confuse this with the H726 / Android 14 path. There the launcher calls the HIDL HAL `vendor.display.config@1.0::IDisplayConfig`, transaction 36, and saves `persist.display.keystone_*`. That is the path battleof3's `app_process` helper drives. It is a different chip and Android version, so that helper should not be expected to work on the HY320 as-is.

## How automatic keystone behaves (HY310 stock)

- It is not a continuous control loop (the Linux port's reading of the vendor logic). The "run once after a move of 3 degrees, then 2 seconds still" rule in that doc is the port's own tool, not the vendor's. What triggers the vendor's run is not stated; the code shows a 0.3 degree dead band on tilt and a kernel hook named `shake_for_vafocus`, so it probably reacts to tilt changes. (Corrected by the checker; medium.)
- It measures tilt against a stored "level" reference pose, then turns the tilt into four corner insets using the optics constants in `camprjspe.ini`.
- On camera-equipped models the camera angle can also feed in. The HY320 has manual focus and no confirmed camera, so it would rely on the tilt sensor alone (inference).
- The prior H713 data point fits this picture. With LuminaOS disabled on an HY300 Pro+, "basic keystone correction still works" but the advanced vertical correction screen was gone. That is consistent with vafocus doing the automatic part on its own, but the report does not say which part survived. (Low to medium.)

## What this means for the plan

- **Keep-list:** add `com.hysd.vafocus`, its `libduRYXtp.so`, `/system` `libkeystone.so` and the modified SurfaceFlinger (stock system, so it stays anyway), the accelerometer driver, and `camprjspe.ini`. Do not delete vafocus on the grounds that the HY320 has manual focus.
- **Launcher:** if it goes, the manual keystone screen and the orientation screen go with it. Automatic keystone probably stays.
- **Own keystone app (the map's "only if needed" item):** it is probably needed for manual keystone if the launcher is removed, and its interface would be SurfaceFlinger transaction 1050, not the H726 HAL. It may need the system UID to be accepted, which is unknown. Orientation is a separate unknown that an own app might not be able to drive.
- **Possible sign the launcher must go:** micha102's HY300 Pro, with a `ui_Veng.projector` build like this unit's, ships `com.htc.htclauncherhighenglishd08`, which that source calls malware. If the HY320 ships the same launcher, the manual keystone and orientation screens live in a component that must be removed. (Low to medium: the source is unverified and AI-written.)

## To confirm on this unit

These are reading tasks. Read the golden backup on the PC: unpack and inspect it, never run anything from it. Use only read-only commands on the live unit.

From the golden backup, offline:
1. Which launcher package is present (`/product/app`, `/system/priv-app`), and whether its manifest declares the keystone and projection activities, and whether those are exported. A non-exported activity cannot be opened from another launcher.
2. Whether `com.hysd.vafocus` is present, and from its manifest: `sharedUserId` (system?), its `LocalService`, a `BOOT_COMPLETED` receiver (does it start by itself?), `VajzActivity`, and whether it bundles `libduRYXtp.so` and `camprjspe.ini`.
3. Whether `/system/lib/libkeystone.so` exists, and whether `libsurfaceflinger.so` contains `getKeyStoneMatrix`. A string search for `persist.htc.keystone` versus `persist.display.keystone` across the system image shows which keystone path this build uses (H713-style or H726-style).
4. The `/oem` (media_data) `config.ini` values for `autoKeystone` and `manualKeystone`.
5. The accelerometer node on twi1 in the device tree.

On the live unit, read-only, inside the map's allowed steps (ticket 07):
6. `getprop | grep -i keystone`, to see the property names and the current values.
7. `dumpsys package com.hysd.vafocus` and `dumpsys activity services com.hysd.vafocus`, to see whether its service is running and what starts it.
8. `getprop` and `settings list global` / `system` / `secure`, saved before and after changing the projection mode and the auto-keystone switch in the stock UI, then compared, to find where those are stored. Changing the mode is a settings change and needs the user's yes.
9. Whether keystone also bends the HDMI input picture (the Chromecast). The warp is in SurfaceFlinger, and it is not proven that the HDMI video layer passes through it.

After cleaning, a test that settles the main question: with the launcher disabled (a reversible step, with its undo), reboot, tilt the projector, wait, and see whether the picture straightens.
